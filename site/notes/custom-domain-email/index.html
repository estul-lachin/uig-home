Free email on your own domain, with SPF, DKIM and DMARC passing

11 November 2026 · about 8 minutes

I wanted recruiters to reach me at hello@uig.me instead of a Gmail address. I had four requirements:

  • No cost. No paid mailbox.
  • One inbox. I keep reading and writing in Gmail.
  • Replies authenticate as uig.me. A reply must pass DMARC for my domain, and the recipient should not see "sent via gmail.com".
  • DNS stays where it is. Five sites on GitHub Pages hang off this zone, so moving it to another DNS provider was not worth the risk.

The result has two halves: forwarding for incoming mail, and an SMTP relay for outgoing mail. Both halves run on free plans. Below are the setup, the DNS records, and the message headers that show it works.

How it fits together

Incoming

  1. Senderany mail server
  2. uig.me MXregistrar's free forwarding
  3. Gmailfilter: never spam, label uig.me

Outgoing

  1. Gmail"Send mail as" hello@uig.me
  2. Brevo SMTP relaysigns with DKIM d=uig.me
  3. Recipientchecks SPF, DKIM, DMARC

The DNS records

This is the whole mail part of the zone. Spaceship, my registrar, added the MX and SPF records itself when I turned on forwarding. I added the rest from what Brevo showed me.

NameValue
@ MX mx1.efwd.spaceship.net and mx2.efwd.spaceship.netReceive mail and forward it
@ TXT v=spf1 include:spf.efwd.spaceship.net ~allSPF: which servers may send with a uig.me envelope sender
@ TXT brevo-code:…Proves to Brevo that I own the domain
brevo1._domainkey CNAME b1.uig-me.dkim.brevo.comDKIM public key; the CNAME lets Brevo rotate it
brevo2._domainkey CNAME b2.uig-me.dkim.brevo.comSecond DKIM key
_dmarc TXT v=DMARC1; p=none; rua=mailto:rua@dmarc.brevo.comDMARC policy, and where aggregate reports go

Two things to watch in the registrar's form:

  • A domain has only one SPF record. If a provider asks you to "add" SPF, edit the existing record and add another include: to it. Two v=spf1 records make SPF return permerror.
  • The host field is usually relative. Spaceship appends .uig.me itself. If you paste brevo1._domainkey.uig.me, you get a record named brevo1._domainkey.uig.me.uig.me. I checked for this with dig @launch1.spaceship.net brevo1._domainkey.uig.me.uig.me CNAME.

Why Brevo is not in the SPF record

This surprised me at first. DMARC passes when either SPF or DKIM passes and is aligned, meaning its domain matches the domain in the visible From: header.

  • SPF checks the envelope sender (Return-Path). Brevo sets that to its own bounce domain, gx.d.sender-sib.com, so it can process bounces. SPF passes, but for Brevo's domain, so it is not aligned with uig.me. Adding Brevo to uig.me's SPF record would change nothing.
  • DKIM is signed with d=uig.me, using the key behind the brevo1._domainkey CNAME. It passes and is aligned, so DMARC passes.

This is also why I did not send through Gmail's own servers. A message sent that way is signed d=gmail.com and has a gmail.com envelope sender. Neither aligns with a From: of uig.me, so DMARC for my domain would fail.

Setting it up

  1. Forwarding. In the registrar's email settings, forward to a single address, my Gmail. Spaceship sent no confirmation email; the MX records were live within minutes.
  2. Keep forwarded mail out of spam. My first test landed in Gmail's spam folder, which is common for forwarded mail. Create a Gmail filter with To: @uig.me, then Never send it to Spam and Apply label.
  3. Brevo domain. Add the domain, choose manual authentication, copy the records into DNS, then verify.
  4. Brevo sender. Add hello@uig.me as a sender. The verification code arrives through the forwarding you just set up.
  5. SMTP key. Generate one under SMTP & API. The SMTP login looks like …@smtp-brevo.com; it is not your account email. When Brevo asked whether to block SMTP from unauthorized IP addresses, I said no: Gmail connects from many changing addresses that cannot be listed. The protections that remain are a key that lives only in Gmail, two-factor auth on the Brevo account, and revoking the key if it leaks.
  6. Gmail "Send mail as". Settings → Accounts and Import → Add another email address. Use smtp-relay.brevo.com, port 587, TLS, with the SMTP login and key. Then set Reply from the same address the message was sent to.

Reading the headers

The copy in your own Sent folder is the message before it reaches the relay, so it has no authentication results. Open the message on the recipient's side and view the source. Below are the relevant lines from my first test, as received by Outlook.com. I have shortened them and removed the recipient.

Return-Path: bounces-…@gx.d.sender-sib.com
Authentication-Results: mx.microsoft.com 1; spf=pass (sender IP is 77.32.148.24)
 smtp.mailfrom=gx.d.sender-sib.com; dkim=pass (signature was verified)
 header.d=uig.me;dmarc=pass action=none header.from=uig.me;compauth=pass reason=100
DKIM-Signature: v=1; a=rsa-sha256; c=relaxed/relaxed; d=uig.me; s=brevo1; …
From: "Estul Lachin" <hello@uig.me>
X-MS-Exchange-Organization-SCL: 1
X-Microsoft-Antispam-Mailbox-Delivery: … dest:I …
spf=pass smtp.mailfrom=gx.d.sender-sib.com
SPF passed for Brevo's bounce domain. It is real but not aligned with uig.me, as explained above.
dkim=pass header.d=uig.me
The signature verified against the key at brevo1._domainkey.uig.me. This is the aligned pass that DMARC relies on.
dmarc=pass action=none header.from=uig.me
DMARC passed for the visible sender's domain. action=none reflects my current p=none policy.
compauth=pass reason=100
Microsoft's composite verdict, which combines SPF, DKIM, DMARC and its own signals. A reason code in the 100s means the message passed.
SCL: 1 and dest:I
Spam confidence level 1 (0 and 1 mean not spam), delivered to the Inbox rather than Junk.

The same check at Gmail, in a second test, read dkim=pass header.i=@uig.me header.s=brevo1 and dmarc=pass (p=NONE sp=NONE dis=NONE) header.from=uig.me.

Where the first message spent nine minutes

The first test took about ten minutes to arrive. The Received headers, read from the bottom up, show where the time went:

Received: by mail-dy1-f178.google.com … ; Wed, 11 Nov 2026 09:07:07 -0800 (PST)   # Gmail hands it to the relay: 17:07:07 UTC
Received: from gx.d.sender-sib.com (77.32.148.24) by …outlook.com … ; 17:16:24 +0000  # Brevo delivers to Outlook
X-MS-Exchange-Transport-EndToEndLatency: 00:00:04.09                                  # Outlook to the mailbox: 4 s

The relay held the message for nine minutes, which is common for a brand-new account. Outlook needed four seconds. In the second test, the hand-off to Brevo and the arrival at Gmail were two seconds apart.

Gotchas

  • Do not test by sending from the same Gmail. When a message you sent comes back through forwarding, Gmail treats it as the same message and keeps only the Sent copy, so it looks as if forwarding is broken.
  • The free relay adds tracking. Brevo inserts a hidden open-tracking image and a List-Unsubscribe header, which can make mail clients show an "Unsubscribe" link next to my name. Its "anonymous tracking" setting only stops linking opens to contacts; the image stays. I accepted this for now. If it matters to you, choose a relay that lets you turn tracking off.

Next: enforcing DMARC

With p=none, receivers report on mail claiming to be from uig.me but still deliver it, even when it fails. After a week or two of aggregate reports showing that Brevo is the only legitimate source, I will move to p=quarantine and then to p=reject. From then on, receivers will refuse a forged From: …@uig.me.

This is the same evidence a SOC analyst reads when triaging a reported phishing email. A spoofed message from my domain would show dmarc=fail header.from=uig.me, with a Return-Path and sending IP that have nothing to do with Brevo. Setting up the passing case myself made the failing case much easier to recognize.
